Q1 · choose one ✓ answered

Comment rail placement

Where feedback-mode comments live on wide screens.

When you review a document in the browser, your comments have to be shown somewhere. Today they appear directly under the paragraph they belong to, which pushes the text apart. The redesign moves them out of the text — the question is where.

Margin-aligned cards means each comment floats in the right margin at the same height as the sentence or element it refers to — like handwritten notes on a printed draft. You always see note and text together, but with only one or two comments the margin looks mostly empty.

Compact top-right list means all comments stack in one tidy list in the corner, like an inbox. Nothing is ever sparse, but to see what a comment refers to you must click it and the page jumps there.

This is purely about reading comfort — both options carry exactly the same data.

Q2 · single choice ✓ answered

Feedback schema migration

The new target model changes the comment shape. The only consumer is Claude reading the feedback file.

When you submit comments from the browser, they are saved in a small file with a fixed format ("schema") that Claude then reads. The new element-level commenting changes what a saved comment looks like inside that file.

Normally, changing a saved format is risky because other programs that read the old format break. Here there is exactly one reader — Claude, in the same session — so nothing outside this plugin can break.

Change in place: switch to the new format cleanly, no leftovers. One release: write both old and new formats side by side for a while, then delete the old one — extra safety, extra cleanup work. Keep indefinitely: both formats forever, and every future reader must understand both.

Q3 · architecture change ✓ answered

Split the browser selection layer into a shared asset

Anchored commenting (select text, click an option or a diagram node) is one behaviour needed by two pages. Should it move into a shared file both modes load?

The feedback page and the ask page are driven by two separate JavaScript files. The new "comment on exactly this thing" behaviour is the same job on both pages. If each file grows its own copy, the two copies drift apart and every fix must be made twice.

Agree means: create one shared file (shared/selection.js) that both pages load — one implementation, fixed once, behaves identically everywhere. The cost is a small refactor of both existing files now.

Disagree means: keep each page self-contained and accept the duplication — no refactor now, more maintenance later.

Q6 · scale ✓ answered

How far should the visual redesign go?

1 keeps the current Editorial theme with small fixes; 5 adopts Proof everywhere including the ask and feedback assets.

The plugin's pages currently use a warm cream look ("Editorial"). The prototypes use a cooler look ("Proof") where everything you add is drawn in pencil blue. This slider says how much of that new look should actually ship.

1–2: keep the current look, only fix real problems (contrast, spacing, wasted screen space). 3: new look for the visualize pages only, forms stay as they are. 4: new look everywhere except deliberately kept details. 5: full adoption — every page, form, and template moves to Proof in this PR.

Higher numbers mean a bigger, riskier PR but one consistent look; lower numbers mean less churn now and a mixed look for a while.
